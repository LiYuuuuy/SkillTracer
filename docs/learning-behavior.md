# Learning behavior

This records historical learning rules that remain in use. It does not impose
legacy parity on future changes. The current planner guard and two-stage
assessment protocol are defined in [skill reuse and assessment](skill-reuse-and-assessment.md).
Current [alignment rules](behavior-alignment.md) supersede historical absolute-index
repair progress, live failure-node aliases and promotion of the next failure's repair.

This audit uses the source snapshot taken before the refactor, specifically
`workflow.py`, `memory/memory.py`, `component/component.py`,
`skill/skill.py`, and the planner, subgoal, skill and repair agent implementations.
Source hashes for the executable learning and memory references are recorded in
`tests/fixtures/learning_reference.json`. The backup is not required to run tests.

## Generation and persistence

| Asset | Generation or update condition | Visibility | Persistent reusable bank |
| --- | --- | --- | --- |
| Skill | At a subgoal boundary: at least two verified nodes accumulated for that subgoal; executor steps below the task limit; planning rounds at most 20 | Staged separately; retrieval uses the bank loaded at task start | `skills.txt`, after final task success |
| Component type | Same budget and planning-round gates; learn each nonempty `(purpose, component_type)` from the verified subgoal plan; no minimum node count | Registry cache is updated; planner recommendations are captured when the workflow is constructed | `components.txt`, immediately at the eligible subgoal boundary |
| Active memory | An explicit `memorize(bid)` action creates an observed-subtree record with source URL and node description | Shared within the task; captures have independent IDs; rollback removes only failed-suffix records | Task assets; not reloaded across tasks |
| Short-term memory | A repair creates or updates a failure record; scoped to the current subgoal | First failure is retained but not used as prompt context; repeated failure without progress makes an editable record usable | Task assets; not a cross-task bank |
| Long-term memory | A repair transition already has short-term history and newly verifies at least one node before the next failure; promote the prior repair and insight | New entries are staged; repair context remains the task-start snapshot of the most recent five bank entries | `memory.txt`, after final task success |
| Subgoal memory | Keep completed subgoals' nonempty, non-Null guidance from their final planning round | Task-start retrieval: top five similar historical tasks | `subgoals.txt`, after final task success; all-Null guidance leaves it unchanged |

The skill threshold is `>= 2`, despite an original comment saying “bigger than
2.” The task-wide node count and final evaluation do not initiate induction.
Two plans with one verified node each can induce a skill if they belong to the
same subgoal. Two separate one-node subgoals cannot. A generated skill with an
existing ID replaces that entry; a new ID is normalized to the next `sN` ID.

The original planner described registered component types as recommendations,
not an exhaustive set. A newly observed type may be used by the planner, or a
component-type repair may request a different observed type. The registry learns
the type only from the subsequent verified plan, not from the repair request alone.
Known types are deduplicated and unrecognized purposes are ignored.

The planning loop can enter a 21st round, but the original learning block is
guarded by `stuck_saver <= 20`. The implementation preserves this boundary.
Reaching the executor step limit also suppresses both skill induction and type
updates, including when the last action completes the subgoal successfully.

## Repair memory transitions

1. First failure: create one editable, non-usable short-term record.
2. Another failure with `progressed_nodes == 0`: update its failed node; if it is
   editable, append the attempted repair and mark it usable. Otherwise append
   a new non-usable record.
3. A later failure with `progressed_nodes >= 1`: before changing short-term
   memory, promote the preceding short-term record to a long-term entry when a
   signal and insight exist. Freeze the preceding short-term record and append
   a new non-usable record for the current failure.
4. A successful assessment does not call these memory update routines. Success
   alone therefore does not produce short-term or long-term memory.

`progressed_nodes` now counts newly verified prefix nodes in the current batch,
excluding the earlier committed prefix. Promotion stores the prior repair that
enabled this progress. The historical index-based/current-repair behavior is
retained only as a reference fixture. Failure records are immutable snapshots.

Guidance is generated by the repair agent. Successful assessments contribute
`Null`. Guidance is reset when a new plan is requested, as in the original loop;
earlier guidance remains in the asset event journal even when not banked.

## Refactor corrections and verification

The audit corrected unintended differences:

- Component types had been gated on final task success. They now commit at the
  original eligible subgoal boundary, including before a later failure.
- Type updates now respect both original learning gates, and the 21st planning
  round cannot induce a skill.
- Newly promoted long-term experience is no longer fed into the current task's
  repair prompt. It is available to subsequent tasks after a successful commit.
- Subgoal guidance again uses the final planning round, and the planner prompt
  again permits observed types outside the existing recommendations.
- An empty final plan now carries its completion metadata into the accumulated
  verified plan supplied to skill induction, as in the original composition.

The reference fixture was obtained by executing the original guarded learning
block for 36 combinations of node count, step count and planning rounds. Its six
repair transitions and three subgoal-memory updates were executed against the
original memory classes. Tests compare these expected outputs to the new code.
Workflow regressions also distinguish two plans in one subgoal from two separate
subgoals and check component persistence after failed evaluation or exceptions.

The refactor retains explicit corrections to execution bookkeeping: verified
progress remains visible when the step budget ends, memory actions observe the
page at their position in action order, and repair targets are resolved before
rollback. The current [node recovery rules](node-identity-and-retrieval.md) restore
a first-uncommitted-node fallback for invalid references. These are distinct
from the learning gates audited above.
Prompt wording can change model decisions, so these checks establish control-flow
and learning-rule parity, not identical live trajectories or full benchmark
equivalence.

Every attempt records `learning_decision` events and the same decisions in
`skills.json`: verified node count, steps, planning rounds, induction choice,
component-update choice and explicit skip reasons. `manifest.json` records
per-bank commit flags; `learning_committed` refers to the task-success skill and
experience commit, while components may already have been committed separately.

## Domain storage and producer records

The user-requested storage policy now places these banks under
`<state-root>/<domain>/` and starts new domains empty. Skills and all memory and
component retrieval/writeback use that domain only. Historical packaged learning
banks have been removed and archived locally. Skill retrieval is now eligible
with any nonempty bank. `top_k=3` is a candidate upper bound rather than a
minimum bank size; one or two committed skills can already reach the reuser.

Attempt assets under `<results-root>/<domain>/assets/<task>/<attempt>/` record
only produced or changed entries. They do not copy loaded banks or enumerate
initialization. Long-term entries are captured at the promotion transition;
component discoveries are captured before their immediate write and receive
provenance at that commit. Task-success banks receive provenance only after
their respective successful write. Failed-task candidates remain inspectable
without becoming reusable. See [asset management](asset-management.md).
